# Restarting on another host

Use this page if the lab host (`DESKTOP-SLQMEQH`, see [GPU_HOST_HANDOVER.md](GPU_HOST_HANDOVER.md)) is lost or replaced. It rebuilds the mpr setup on another machine and continues the queued experiments. Everything the host holds that the experiments still need is kept on the hub or on the laptop. This page says where, and gives the order to put it back.

Written on 2026-10-03. Systems only: none of this changes a filed number, and a new machine is a new placement (step 4).

`outputs/host_ops/coverage_latest.json` classes every host file: `hub`, `records`, `delete_list`, `in_flux` (a running job's, or modified in the last 30 min) or `uncovered`. `host_sync.py` archives the uncovered files every 6 h. Between two archive runs, a host loss can cost what jobs wrote since the last one. Results come to the laptop every hour; other files are regenerated by rerunning the jobs that wrote them.

Tokens are chosen by name on the laptop: `mpr` for KK9895, `mpr-archive2` for JGY9895, `freebase` for Swastik9895. A token never goes to a host.

## What the new host needs

- **Windows, with rx's home at `C:\Users\Student2\rx`.** `configs/host_mirror_six.yaml` declares the mirror root as `C:/Users/Student2/rx/projects/mpr/mirror/CRAG`, and every host stage reads the mirror there. On a machine with another account, the owner either makes that path exist (a directory junction) or files a dated amendment to that declaration first. Both are the owner's actions.
- **Memory and CPUs.** The queued jobs reserve up to 27 GB and 4 CPUs each. The feeder keeps mpr within `--cap-cpus 26 --cap-mem 104`; lower both to fit a smaller machine.
- **Disk.** About 300 GB: the mirror 69 GB, the outputs about 80 GB, the environments 11 GB, and room to grow.

## Steps, in order

1. **Route.** The owner points the ssh alias `gpu` in `~/.ssh/config` at the new machine. Reusing the alias leaves `rx.toml` as it is. A new alias needs `[project] host` in `rx.toml` changed instead; never edit the `[envs.*]` tables.
2. **rx.**
   ```bash
   python tools/rx/rx.py setup gpu
   ```
   Then check it with:
   ```bash
   python tools/rx/rx.py doctor
   ```
3. **Environment.**
   ```bash
   python tools/rx/rx.py env build mpr-cpu -f
   ```
   The same `[envs.mpr-cpu]` table builds the same address, `mpr-cpu@31803e6457ab`. Compare `python tools/rx/rx.py exec --env mpr-cpu -- python -m pip freeze` with [host_env/mpr-cpu_31803e6457ab.freeze.txt](host_env/mpr-cpu_31803e6457ab.freeze.txt).
4. **Placement.** The equivalence verdict that lets a stage name the host CPU is for `DESKTOP-SLQMEQH`. On a new machine, run [`configs/cpu_gpu_equivalence.yaml`](../configs/cpu_gpu_equivalence.yaml)'s test there, at 8 BLAS threads per process, before a stage names it. `compile_query_v2` features change with the OpenBLAS thread count, so any laptop reference for a host-compiled batch is packed at the host's count.
5. **Data.** First list the steps:
   ```bash
   python scripts/host_restore.py plan
   ```
   Then run them:
   ```bash
   python scripts/host_restore.py run
   ```
   The order:
   - `mirror-spared` into `../mirror`.
   - The five mirror downloads. For each, the laptop resolves signed links with `host_mirror_hf.py urls`, and the host downloads and then verifies (sha256 and the served-freeze check `58958f33…`).
   - Every workspace tag of both archive repos, newest manifest first, into the workspace. A file an older tag holds at other bytes is left at the newer version.

   A rerun resumes after the last finished step (`outputs/host_archive/restore_progress.json`). The hub serves about 70 MB/s to the old host on large files, so expect one to three hours.
6. **Check.**
   ```bash
   python outputs/host_ops/host_sync.py --once --dry --mirror
   ```
   Every restored file should class as `hub` (restored files have new mtimes, so their sha256 is checked on the host), and the mirror should read 577/577.
7. **Queue.** Stop the feeder. List what goes back to the queue:
   ```bash
   python outputs/host_ops/requeue_after_host_loss.py outputs/host_ops/scratchpad/feeder_items.txt outputs/host_ops/scratchpad/feeder_state.json
   ```
   Then run the same command with `--apply`. Items whose job was running or queued in the last saved job table go back to the queue. Finished items keep their place, and their state is recorded so that dependent items don't ask the new host about an id it has never seen. Restart the feeder from `outputs/host_ops/scratchpad/` (it finds its jobs files beside itself), with caps that fit the new host.
8. **Sync.** Restart the loop:
   ```bash
   python -u outputs/host_ops/host_sync.py >> outputs/host_ops/host_sync.log 2>&1
   ```
   Run it in the background.

## What the loop does while the host is up

`outputs/host_ops/host_sync.py` runs on the laptop.

Every hour it:
- copies the session scratchpad's small files (the feeder, its queue and state, the jobs files, the wave scripts, the logs) to `outputs/host_ops/scratchpad/`;
- saves the host's job table and each finished job's log;
- fetches finished jobs' results and models by exact path, with rx's own fetch:
  - It skips a running job's files and anything modified in the last 30 min.
  - It never writes a delete list's files or into a filed stage's laptop outputs.
  - It takes at most 2 GB per cycle.
  - Models stop at 15 GB free on the laptop, and everything stops at 5 GB.

Every 6 hours it:
- runs the coverage check;
- archives the uncovered files to `JGY9895/mpr-host-archive` as one `o-inc-<stamp>` tag;
- uploads the ops snapshot.

It never deletes anything, and it changes no file on the host.

## Not covered

- **Jobs running when the host is lost.** Step 7 resends them.
- **Host files written since the last 6-hourly archive that are not results.** Rerun the jobs that wrote them.
- **The laptop itself.** It holds the only copy of the code: origin on GitHub is behind, and pushing is the owner's call. The ops state also has a hub copy (`ops/host_ops.tar.gz`).
