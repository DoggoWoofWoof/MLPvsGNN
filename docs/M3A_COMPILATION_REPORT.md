## What was asked, and what this returns

The phase was asked for a five-dataset compilation and headroom report. The
compilation half is here. The headroom half is not, and the reason is worth
being precise about: **it is not blocked on code.**

`headroom_metrics` in `src/mp_retrieval/candidate_headroom.py` already computes
candidate ceiling, ANY, ALL/FullCov, `recall_ceiling@K` for any K, `hit_ceiling@K`,
`ndcg_ceiling@K` and queries-with-no-gold-in-pool. `headroom_v2.regime_headroom`
already wraps that per regime. Every quantity the phase asked for exists as
working, tested code.

What does not exist is the input: a candidate pool. That needs queries and
retrieval, and two blockers stand in the way. Both are now measured, and both
are cheap.

## What the substrate already settles

### The hub problem, which is one problem and not three

Directions A, C and D all define features by expanding from a node. They
therefore all meet the same wall:

| dataset | max degree | 2-hop walks from that one node |
| --- | ---: | ---: |
| metaqa | 4,176 | 17,438,976 |
| squad | 2,524 | 6,370,576 |
| musique | 14,364 | 206,324,496 |
| hotpotqa | 189,410 | 35,876,148,100 |
| 2wiki | 158,048 | 24,979,170,304 |

On hotpotqa and 2wiki an unbounded 2-hop neighbourhood is not expensive, it is
impossible. This is a design constraint, not a tuning parameter:

- Direction C's radius bound belongs in its **definition**, not its config.
- The bound must be **deterministic** -- a sampled neighbourhood is not a fixed
  aggregation, and C's whole claim is that the graph chooses which vectors
  contribute while the combination stays fixed. A top-m-by-fixed-criterion cap
  keeps that; random sampling does not.
- Direction A's `distance_3_plus_or_unreachable` split has the same cost. A
  bounded frontier is needed to tell 'far' from 'unreachable' at all.

### Direction B is metaqa-only by necessity, not by authorisation

Only metaqa has more than one relation type. Every other dataset in this
substrate has exactly one, so there is nothing to type anywhere else.

That is stronger than the declaration assumed, and it cuts the other way from
how it sounds: it means a metaqa result would be the **only** typed-relation
evidence these five datasets can produce. A null there would be one dataset,
9 relation types, normalised entropy 0.8349 -- against WebQSP's 7,058 types.
`FINAL_TYPED_RELATION_BLOCK` stays `PROVISIONAL`, and this is the measurement
that says why.

## Recommendation

Apply the project's own compute rule -- validate cheaply first, expand only
when the current scale produces evidence that more compute can change a
scientific decision. That rule has an unusually clean answer here.

**Three of the five datasets need no build at all.** squad, musique and
hotpotqa already have canonical queries, query encodings and document
encodings. Retrieval on those three costs:

- **0.014-0.057 GPU hours**, about $0.06, and produces a real headroom table

That is enough to answer the question the deferral was made for -- whether the
compiled-graph MLP idea is promising -- on three datasets spanning a
259x range in corpus size (20,233 to
5,233,329 documents), before anything is built.

Only if that evidence warrants it does the metaqa/2wiki query view get built
(0.20-0.60 GPU hours, $0.66), and only then does WebQSP's gate become
evaluable.

## The WebQSP return gate

The gate opens if any of three conditions holds. **None can be evaluated yet**,
because all three require ranker or aggregation measurements that blocker 2
prevents:

1. compiled features materially improve the non-MP ranker -- no ranker has run
2. fixed aggregation looks competitive enough to be worth a GNN delta -- not measured
3. typed relation summaries on metaqa show signal -- needs metaqa queries

Per the declaration: if none holds, stop and review before spending WebQSP
compute. None holds. **Do not spend it.**

## Decisions this needs

1. **Authorise retrieval on the three ready datasets?** It is a build -- it
   creates candidate pools -- so it is flagged rather than assumed, by the same
   standard that made a WebQSP query set need its own authorisation.
2. **Authorise the metaqa/2wiki query view build?** Recommended *after* (1),
   not with it.
3. **Top-K depth for the pools.** This sets the candidate budget, and the phase
   is required to find knees rather than explode budgets. Recommend sweeping K
   and reporting the curve rather than fixing one K up front.
4. **Neighbour direction for Direction C** -- in, out, or union. The graphs are
   directed, so this is a real choice with three different answers.
